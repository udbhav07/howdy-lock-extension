# Design: Wrong-password photos app (Presence Guard UI)

Generated by /office-hours on 2026-11-28
Branch: main
Repo: udbhav07/howdy-lock-extension
Status: APPROVED
Mode: Builder

## Problem Statement
`presence-guard` (a systemd user service for KDE Plasma 6 + Howdy) now takes 5 RGB photos on each wrong lock-screen password and opens them in Gwenview at the next unlock. The owner wants a proper local app instead. It needs a menu with pages, an on/off toggle for the feature, a stored history of every attempt (photos + timestamp), and a way to see the new attempts right after unlocking. The current system must stay fully working and be easy to extend. The project is going open source, so it has to work on other people's laptops, not only the author's.

## What Makes This Cool
The unlock moment: you sit down, unlock, and a notification shows the face of whoever tried to get in while you were away, with one click to see all of them. The owner's own words: "when real user comes and enter correct passowrd this application should open and show the latest photos and their timestamps".

## Constraints
- KDE Plasma 6 on Wayland, systemd user session, Howdy installed (IR camera via `device_path`).
- No root and no PAM changes for the photo feature.
- Use what is installed: Python 3, PySide6 6.11, OpenCV, dlib, `notify-send` 0.8.8 (supports `-A` action buttons and prints the clicked action to stdout).
- The daemon must stay light. Qt is imported only by the UI process.

## Premises
1. Wrong passwords are detected from the lock screen's own journal lines (`_COMM=kscreenlocker_g`, `pam_unix(kde:auth): authentication failure`), so no PAM edits and no root are needed.
2. The user picks the RGB camera on the Settings page from a list of the cameras found. There is no auto-detection, and photos stay off until a camera is chosen. (Revised: the user rejected auto-detection.)
3. Intruder photos are personal data. They are stored in `~/.local/share/presence-guard/` with 0700 permissions, not in `~/Pictures`.
4. Open-source users get a one-command `install.sh`: it checks dependencies, links the script and the `.desktop` file, and enables the service. No distro packaging yet.

## Cross-Model Perspective
An independent Claude subagent (no access to this conversation) did a cold read:
- Coolest version: tell "you mistyped" apart from "someone else tried" using timing (a correct unlock soon after the failure) and only make noise for strangers.
- What excites the owner: the unlock moment matters more than the gallery.
- Already exists: Howdy's failed-face snapshots (these are IR images of failed face matches, so they don't cover wrong passwords), Android "intruder selfie" apps as a UX model, and KDE notifications with an action button.
- Engineering findings, all adopted below: the first plan contradicted premises 2, 3 and 4. There's a race where an attempt still being written at unlock is never shown as new. Bursts of failures should merge into one attempt. Pass display env vars to `systemd-run`. Also prune when the UI starts.
- Rejected: hiding likely typos entirely. An intruder followed 15 s later by the owner's unlock would vanish, so typos are labeled instead.

## Approaches Considered
- **A) Minimal (script + ui.py).** Rejected: the UI would import helpers from a script without a `.py` extension, which is awkward to test and extend.
- **B) Small package + tests, app opens itself at unlock.** Rejected by the owner in favor of C.
- **C) Notification-first (chosen).** Same package layout as B, but at unlock a KDE notification appears instead of a window popping open.

## Recommended Approach
Approach C. Wireframe: projects/udbhav07-howdy-lock-extension/udbhavsai07-main-sketch-20261128-023157.png (approved).

### Layout
```
presence-guard            entry script: daemon + CLI (check, idle, photo, ui [--since TS])
pg/__init__.py
pg/store.py               the one owner of paths, settings, attempts and their metadata
pg/system.py              kde_lock_seconds() (moved), service_active(), list_cameras()
pg/ui.py                  PySide6 app: sidebar menu + QStackedWidget, PAGES list
presence-guard.desktop    app-menu entry (Exec=presence-guard ui)
install.sh                dependency check, symlinks, .desktop, systemctl --user enable --now
test_store.py             unittest for pg/store.py
```
`presence-guard` puts its real directory on `sys.path` (it is symlinked into `~/.local/bin`) and imports `pg`.

### Data
- `~/.local/share/presence-guard/attempts/<YYYY-MM-DD_HH-MM-SS>/` holds `1.jpg … N.jpg` and `meta.json` (`{"failures": n, "first_failure": <epoch>, "last_failure": <epoch>, "photos": k, "error": null|"<text>", "probably_you": false}`).
- Ownership: the daemon's single **worker thread** is the only code that creates attempts or updates `meta.json`. Deleting is allowed from the UI (Delete button) and from `store.prune()` (UI start and daemon unlock). `prune()` skips `*.partial` and any attempt whose `last_failure` is under 2 min old (its burst may still be open). A burst update that finds its attempt gone treats the burst as ended and starts a new attempt.
- Each attempt is written into `<ts>.partial/` and then renamed, so readers never see half an attempt.
- All small files (`meta.json`, `settings.json`, `last_seen`) are written atomically by `store.py` (temp file in the same dir + `os.replace`), so live readers (the daemon reading settings, the UI's file watcher) never see a half-written file. A read that fails to parse falls back to defaults.
- `~/.config/presence-guard/settings.json`: `{"wrong_password_photos": true, "camera": null, "keep_days": 30}`. Only the UI writes it. The daemon reads it fresh on every failure. Photos are effectively off while `camera` is null (premise 2).
- `~/.local/state/presence-guard/last_seen`: the folder name of the newest attempt already announced. Only the worker writes it.

### Flow
All attempt work runs on **one worker thread** that takes events from a queue in order. The journal thread and the unlock handler only enqueue, so captures, burst updates and unlock handling can never overlap, and there's no fixed wait for a capture to finish.
```
journal thread: `journalctl -f -n0 -o short-unix _UID=<uid> _COMM=kscreenlocker_g`
  └─ line contains "pam_unix(kde:auth): authentication failure" → queue ("failure", <epoch from the line>)
  (journalctl exits → os._exit(1), systemd restarts the service)

D-Bus monitor (main thread): ActiveChanged(false)  (unlock)
  ├─ stop_howdy()                                   (existing, immediate)
  └─ after a 2 s grace (threading.Timer, covers journal delivery lag) → queue ("unlock", <epoch of unlock>)

worker, per event (each event in try/except: log to stderr = journal, keep going):
  ("failure", t):
     settings unreadable → defaults (camera null → ignore)
     not wrong_password_photos or camera null → ignore
     open burst (no unlock since, t − last_failure < 10 s, t − first_failure < 2 min)?
        yes → failures += 1, last_failure = t   (attempt gone → treat as no open burst)
        no  → new attempt: capture into <ts>.partial → rename to <ts>; this becomes the open burst
              capture writes up to 5 photos; meta.photos = number saved;
              camera fails to open / no frames → photos 0, error "<camera> unavailable"
  ("unlock", u):
     close the open burst
     new = attempts with name > last_seen        (every failure queued before this unlock is already captured)
     each new attempt with last_failure ≥ u − 20 s → meta.probably_you = true (still listed and counted)
     store.prune()
     new not empty → last_seen = newest name;
        notify-send -A open=Open -i <newest attempt's 1.jpg, or "camera-photo" if it has no photos>
                    "N wrong-password attempts" (own thread, waits for the click)
          └─ "open" → systemd-run --user --collect -E WAYLAND_DISPLAY -E DISPLAY -E XDG_RUNTIME_DIR
                        presence-guard ui --since <previous last_seen>
```
- A card with fewer than 5 photos shows the photos it has. A card with 0 shows "No photos: <error>". The Status page shows the newest attempt's capture error, if there is one.
- `presence-guard photo` (test the camera): uses `settings.camera`, exits with an error if none is set, and writes the photos to `~/.local/share/presence-guard/test/` (replaced each run, never an attempt, never announced), then prints that path.

### UI (PySide6)
- `MainWindow`: a sidebar `QListWidget` and a `QStackedWidget`. Pages come from `PAGES = [("Wrong passwords", AttemptsPage), ("Status", StatusPage), ("Settings", SettingsPage)]`, so a new page is one class plus one line.
- **Wrong passwords:** with `--since`, the header reads "N attempts since your last unlock" with a "Show all (M)" button. Otherwise it shows the full history, newest first. Each card has the timestamp, an optional "Probably you" tag, 5 thumbnails (click opens the full image with the default viewer), and Delete with a confirmation. A `QFileSystemWatcher` refreshes the list live, and an empty state explains how the feature works.
- **Settings:** a camera picker with Howdy's IR camera left out. The photo checkbox is disabled until a camera is chosen. "Delete attempts older than N days (0 = keep forever)". Changes save immediately.
- **Status:** service active, KDE auto-lock time, both cameras, whether photos are on, and a "Check camera now" button (`QProcess` runs `presence-guard check`).
- The UI also calls `store.prune()` when it starts.

### Camera list
Candidates are `/dev/v4l/by-path/*-video-index0`, de-duplicated by `realpath` (the usb and usbv2 links point to the same node). Howdy's `device_path` is left out. Each one is labeled with `/sys/class/video4linux/<node>/name` and the node. The stable by-path link is what gets saved.

## Open Questions
- Old test photos in `~/Pictures/failed-unlocks/` are not migrated. The README tells the user to delete them.
- No single-instance guard: clicking Open on two notifications opens two windows. Acceptable for v1.
- Wrong-password photos only cover the KDE lock screen, not SDDM. The service isn't running before login.

## Success Criteria
- With a camera chosen and the toggle on: a wrong password on the lock screen produces one attempt folder with 5 photos and meta.json. The next unlock shows a notification with a thumbnail, and Open shows exactly the new attempts.
- 3 wrong passwords within 10 s produce one attempt with `failures: 3`.
- A wrong password followed by the right one within 1 s is still announced (the worker handles the unlock only after the queued failure is captured, and the 2 s grace covers journal lag).
- A wrong password within 10 s after an unlock starts a new attempt (bursts end at unlock).
- With the camera unplugged, an attempt is still recorded with `photos: 0` and an error, and the notification uses a fallback icon.
- Toggle off, or no camera chosen: no photos are taken.
- Attempts older than keep_days are removed. Delete removes one attempt.
- `python3 -m unittest test_store` passes, and the existing `check` / `idle` behavior is unchanged.

## Distribution Plan
The source is on GitHub (udbhav07/howdy-lock-extension). Users run `git clone`, then `./install.sh`. No CI or packaging in v1; the install script is the channel.

## Reviewer Concerns

No blocking findings remain. The 8 open minor finding(s) below are recorded for the user, not fixed.

### R2-1 — feasibility (minor)

**Problem**

> Persisting from R1-10: the Camera list section still says only "Howdy's device_path is left out". Candidates are by-path links deduped by realpath, while Howdy's device_path is often /dev/videoN or a by-id link, so a plain string comparison would leave the IR camera in the picker.

**Remedy**

> Exclude a candidate when its realpath equals the realpath of Howdy's device_path.

### R2-2 — feasibility (minor)

**Problem**

> Persisting from R1-12: attempt names are still local-time strings (<YYYY-MM-DD_HH-MM-SS>) and 'new' is still a string comparison against last_seen, now a folder name. When DST ends the clock repeats an hour, so attempts made in that hour sort before last_seen and are never announced. The design also does not say whether the folder name comes from the failure's journal epoch t or from the capture start time.

**Remedy**

> Name attempts from the failure epoch t in UTC (or compare on first_failure epochs) and keep local time for display only, or record the DST limit as an accepted shortcut.

### R2-3 — completeness (minor)

**Problem**

> Persisting from R1-13: Next Steps 2 still lists only paths, settings, attempts, partial rename, meta, prune and last_seen for test_store.py. The worker's decision logic (open-burst check with the 10 s / 2 min / unlock rules, computing 'new' from last_seen, probably_you at u - 20 s, prune skipping partials and recent attempts) gets only live checks, although Success Criteria assert exact outcomes such as failures: 3 and 'bursts end at unlock'.

**Remedy**

> Put these decisions in store.py as pure functions that take times as arguments, and test them in test_store.py.

### R2-4 — completeness (minor)

**Problem**

> Persisting from R1-14: notify-send still runs on its own thread inside the service. A service restart (journalctl exits -> os._exit(1), or lost D-Bus) kills it, so Open on a notification still on screen does nothing. Deleting or pruning an attempt also leaves a notification whose icon path is gone. Open Questions does not mention this.

**Remedy**

> Record this as a v1 limit in Open Questions, or start notify-send through systemd-run as well.

### R2-5 — completeness (minor)

**Problem**

> A short capture is now allowed (photos k < 5), and the notification uses '<newest attempt's 1.jpg>' whenever photos > 0. The existing take_photos names files by frame slot, so if the first slot's read() fails and later ones succeed, 1.jpg does not exist and notify-send gets a missing icon path.

**Remedy**

> State that saved photos are numbered 1..k in the order saved (so 1.jpg exists whenever photos > 0), or pick the icon from the first photo that exists.

### R2-6 — feasibility (minor)

**Problem**

> The journal command changes from the existing '-o cat' (presence-guard line 137) to '-o short-unix', and the failure event now depends on parsing an epoch from the line. The probe refused journalctl (not on its allowlist), so the flag is unverified, not disproved. The design also does not say what happens if the epoch cannot be parsed; an exception in the journal thread (a daemon thread) would stop all captures with no signal, which is the R1-4 problem moved to a new thread.

**Remedy**

> Confirm '-o short-unix' on the target journalctl, and specify that a line whose epoch does not parse falls back to time.time() (or that the journal thread os._exit(1)s on any exception).

### R2-7 — completeness (minor)

**Problem**

> The fallback-to-defaults rule is stated for all small files but the defaults are given only for settings.json. For last_seen, a missing or unreadable value would make every attempt in history 'new' and re-announce it. For meta.json, a default last_failure could make prune() delete an attempt it should have kept, or skip one forever.

**Remedy**

> State the default for last_seen (e.g. empty = announce everything, acceptable on first run) and that prune() falls back to the folder name's time when meta.json is unreadable.

### R2-8 — completeness (minor)

**Problem**

> The UI Delete can race a burst update in the same attempt: the worker writes its temp file into the attempt dir while the UI removes it, so rmtree can fail with 'directory not empty' or leave a folder holding only a temp file, or the worker's os.replace fails mid-way. The design only covers an attempt that is already gone when the update starts.

**Remedy**

> Have Delete rename the attempt out of attempts/ (e.g. to a .deleting name) before removing it, and have the worker treat any write error on the open burst as 'attempt gone'.
